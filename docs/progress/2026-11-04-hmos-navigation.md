### 原因与修复边界

原 `find-below.yaml` 只执行向下的 `scrollUntilVisible`。当前 Maestro 中，YAML 的 `direction: DOWN` 对应向上滑动，居中判断只要求目标中心的 y 坐标小于屏幕高度的 70%；即使目标已进入顶部标题栏，也会满足这一条件。`direction: UP` 的检查则要求目标中心的 y 坐标大于屏幕高度的 30%。本屏幕分别对应 y < 1904 与 y > 816。

当前修复保留原向下查找，再执行一次标准 YAML `swipe`，从屏幕 `50%,40%` 滑到 `50%,55%`，持续 1000 ms，通过短距离向下滑动将目标移出顶部标题栏区域。此次行为修改仅限 `common/find-below.yaml`，`find-above.yaml` 原有的 `UP → DOWN` 和驱动实现均沿用原版本，场景与断言保持完整。该修改不增加框架层遮挡判断。

两个限制仍然存在：

- `above` / `below` 实际只比较节点左上角 y，不比较完整边界。标题栏顶部是 y=124，本次四个目标节点的顶部均大于124，所以加上 `below: { id: HdsTitleBar }` 仍会全部通过，不能作为防遮挡条件。
- `centerElement` 超过居中重试上限后，可以按 `visibilityPercentage` 成功返回；可见比例按屏幕范围计算，不能识别其他节点覆盖。短滑的实际位移也受滚动边界和惯性影响。因此这些条件不构成硬边界保证，仍须通过真机回归验证本场景。

## 凌晨批次失败原因

第 1 轮日志记录，“警告弹窗”文字节点边界为 `[299,2474][508,2535]`，点击中心约为 `(403,2504)`。这一位置落在悬浮底栏的“样例”按钮范围 `[383,2460][630,2616]` 内，点击后实际切换了标签页。UITest 树中的 `visible=true` 不足以证明节点没有被覆盖。

原入口仅检查“组件”文字是否可见，而底栏在“样例”页仍包含这段文字。该检查通过后，后续轮次在错误的标签页反复查找输入组件，因而连续失败。

## 凌晨导航修复

- 每轮以 `launchApp.stopApp: false` 保留应用进程，先确认根页面选中的标签，再切到“组件”。页面检查同时要求 `selected: true`。
- 使用标准 `scrollUntilVisible` 和 `centerElement: true` 查找列表项；向上查找后补一次向下的居中检查，兼顾当前 Maestro 版本的方向性判断。查找与点击均限定目标位于已选中的组件标签上方。
- 若前一轮停留在本套件详情页，仅在“预览区域”可见且没有选中的根标签时，允许最多 3 次返回；已打开的警告弹窗先通过其按钮关闭。无法识别页面时保留失败，不继续返回到应用外部。
- 保留输入、按钮样式、警告弹窗的原有操作、参数、条件分支、断言与截图，不减少场景覆盖。

页面恢复不代替数据检查。输入场景仍检查空输入框，按钮场景仍检查 `Emphasized` 初始值；详情数据或应用状态不满足条件时应失败。
