原用例在 `eraseText: 50` 后执行输入，最终未找到 `panda-scroll`。步骤日志显示删除过程约 52 秒，失败截图中目标框仍显示占位提示，布局中的 `focused=false`。这能确认输入没有落入目标框，但不能确认焦点丢失的具体时刻或原因。

随后从同一输入框执行短诊断：点击、确认焦点、删除 1 个字符、再次确认焦点、输入，再按 `test_input` 与完整文本联合断言。诊断通过，退出码 0、清理完成，10 个步骤、7 份引用文件齐全。截图中的浮动键盘没有遮挡输入框。本次成功只覆盖短删除过程，不覆盖原来连续删除 50 次的情况。

公开用例补充清空后重新点击与焦点断言，并将最终文本断言限定到目标控件。首次复测在恢复起始位置的辅助步骤就因未找到“横向滚动”标题失败，修改后的子 Flow 未执行；该次清理正常。原用例失败、短诊断成功及辅助步骤失败分别保留，不合并计算通过率。

弹窗 Flow 的操作与断言全部通过，但最终清理返回 `unknown`，设备暂时阻止接管。134 条设备命令全部确认结束、没有录屏资源，日志的临时文件清单却为空；只读检查发现本次会话目录内仍有一份布局 JSON。该精确路径对应的 `uitest dumpLayout` 和 `rm -f` 参数摘要，均与原日志中已完成的操作记录一致。现有逻辑在逐次删除成功后即移除路径登记，导致最终清理无法再识别这个残留；文件为何在删除应答后仍出现，尚不能仅凭本次记录确定。

源码修复将已登记的布局和截图路径保留到会话最终清理，继续只删除归属明确的精确路径；录屏资源沿用自己的登记和归档规则。补充真实主机 shell 回归，模拟逐次删除成功后布局文件仍存在的情况。前述单页结果使用原冻结 CLI，修复版本另行构建与验证，不覆盖原分发包或原结果。
